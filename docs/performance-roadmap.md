# 性能攻坚与长期开发规划

日期：2026-10-23。基线：main `1e9db27fdd5e077cd49553001ac23cf16b02bae4`（92轮，Sites v91）。

本文是规划，不代表以下机制已经实现。此次仅整理文档，不修改游戏代码、画质、存档、构建或线上版本。后续实施须先核对最新 main，避免覆盖其他开发者的新工作。

**目标：手机优先，在当前清晰度和内容下缩短真正可玩的等待时间，降低移动、转视角和跨区域时的卡顿，并让未来新增内容的成本可测、可控。**

## 1. 现状与判断依据

| 已有证据 | 可以得出的判断 | 不应得出的判断 |
| --- | --- | --- |
| 92轮同画质本机启动约12.326→9.574秒；地图及baseline约2.987→0.091秒 | 地图快照已经解决一块主要重复计算，应转向余下启动阶段 | 手机公网启动已达9.6秒，或总加载已减半 |
| 当前候选在该镜位仍有1,345次绘制、820,434个三角形 | 需要继续分析绘制提交、可见性与对象更新成本 | 所有场景都由GPU或draw calls单一限制 |
| Node构造审计记录约15,046个对象、11,669个mesh、4,025种geometry对象、3,761种material对象、605个texture对象 | 应检查资源是否重复构造、静态物件是否保留了不必要的逐帧工作 | 这些全在同一帧绘制，或能直接换算手机显存 |
| 旧正式版本Pura70/Edge采样约10–11FPS；道路、交通、船体和矩阵/驱动查询是热点 | 已有真机依据，91/92已处理其中一部分 | 这是92轮当前帧率，或最新版本已经达到30FPS |
| 44项发布检查通过 | 已有重要行为、存档和构建回归基础 | 具备完整真机性能门禁；功能通过等于足够流畅 |

92轮本机分段时间是定位线索：地图之后，外滩准备至下一阶段约1.20秒，南京路/地铁约0.56秒，豫园及紧接着的系统初始化约1.84秒，登录背景准备至ready约1.59秒。各段包含多项工作，不能直接认定为单个函数耗时。导航到模块开始的约3.93秒也混合下载、解析等成本，不能全部记为网络。

地图数组约56MB，压缩下载约203KB；下载小并不等于运行占用小。项目已有区块网格、实例合批、静态合并、烘焙补光和加载队列，不是尚未采用基础优化。91轮尝试过的颜色重组、静态空间拆分和通用变换缓存有变慢记录，后续不得无新证据重复推广。

依据：[92轮记录](startup-smoothness92.md)、[启动与运行维护](startup-runtime-performance.md)、[真机热点记录](sustained-mobile-performance.md)。本地原始数据在 `.local-data/qa/boot92-comparison.json`、`startup92-scene-audit.json`、`phone91-baseline.json`；不将手机资料或个人存档加入公开仓库。

## 2. 验收口径先统一

### 玩家实际感受到的指标

- **首屏出现**：页面已有可理解的反馈；只衡量反馈速度。
- **进入按钮就绪**：允许启动游戏；沿用旧指标，便于历史对照。
- **真正可玩**：存档恢复、出生附近地面/碰撞/可见街景/必要交互准备好，首次输入能及时响应。此指标不得被提前显示按钮替代。
- **进入后前10秒**：补加载是否阻塞走路和转视角。不能通过把等待搬到游戏开始后伪装提速。
- **跨区就绪**：步行、地铁、游轮、传送和读档分别记录附近场景准备及最长停顿；不能只测瞬移到已缓存区域。
- **持续流畅**：记录帧间隔P50/P95/P99、每分钟超过100ms的卡顿帧、最长停顿及输入响应；平均FPS仅作为辅助。
- **稳定性**：重复跨区后的资源占用是否趋于稳定，有无白屏、资源持续增长、存档异常和交通停摆。

诊断将下载、脚本解析/执行、场景构造、网格生成、文字/图片纹理、GPU上传/首次着色器使用、模拟和HUD更新分开。`renderer.render()`的墙钟时间包含提交和驱动等待，不是独立GPU耗时。GPU计时仅在扩展可用时使用异步查询，不为诊断每帧增加同步回读。

### 固定比较条件

使用同一发布构建方式、设备/浏览器、画布实际尺寸、抗锯齿、画质设置、时间天气、随机种子、路线和存档样例。冷启动、再次进入、版本更新分别计量；缓存清理仅作用于隔离测试数据，绝不清除真实玩家存档。一个时刻只运行一个完整3D测试页。

手机浏览器为第一验收环境，微信另列兼容性结果，电脑作为回归环境。有条件时补一个不同档位手机；Pura70结果不能代表全部手机。电脑CPU限速用于快速筛查，不能视为手机GPU、内存带宽、温控或微信的1:1仿真。[Chrome官方说明](https://developer.chrome.com/docs/devtools/device-mode)

启动基准先做3次有效样本，噪声大才补到5次；运行按固定短路线交替比较基线和候选。关键里程碑做一次5–10分钟持续游玩检查热衰减和资源增长。出现故障保存已完成结果；测试页需支持前后台/返回恢复，不再次依赖容易丢失的临时报告。

### 目标与门槛（提议，须测量校准）

| 项目 | 第一阶段改进目标 | 中期体验目标 |
| --- | --- | --- |
| 手机流畅度 | 当前92基线的慢帧P95耗时降低约20%以上，超过100ms卡顿次数明显减少，争取减半 | 默认清晰度下主要路线稳定接近30FPS；P95帧间隔约40ms以内，P99约67ms以内 |
| 首次真正可玩 | 在明确网络条件下比当前基线缩短20%–30% | 争取比当前基线缩短约50%；先取得真实手机基线再承诺秒数 |
| 再次进入 | 缓存命中及读档路径分别提速 | 不重复创建可复用静态资源，不全图重建未改变区块 |
| 画面与内容 | 同画布、抗锯齿、文字可读性、人数、视距与路线对照 | 无新增建筑缺失、明显弹出、透明物排序错误、NPC同步或瞬移 |
| 内存/资源 | 找到峰值和常驻占用来源 | 往返各区域后缓存有上限，资源数量不无界增长，无内存不足/白屏 |

以上是方向性目标，不是已取得的结果，也不是所有手机的保证。30FPS每帧约33.3ms，需给浏览器和上传突发保留余量；模拟、提交与GPU可能交叠，不能把各计时简单相加。某项优化仅局部函数变快而完整场景更慢时，不采用。

## 3. 实施顺序与结束条件

| 阶段 | 主要交付 | 进入下一阶段的条件 |
| --- | --- | --- |
| A：基线与保护 | 固定路线、分段启动记录、画质指纹、只读性能报告、已有关键回归清单 | 可以可靠回答“时间耗在哪里”；当前版有可复用对照 |
| B：减少持续运行的主要开销 | 按最新采样处理占比最高的1–2项；重点审计静态对象与实例更新 | 同画质完整路线有收益，行为不退步；收益不足则撤回候选 |
| C：减少启动构造 | 复用资源、构建期准备确定性静态内容、近区优先初始化 | 真正可玩更早，前10秒与转头没有把省下的时间重新卡回来 |
| D：区域资源生命周期 | 一个区域试点按需准备、预取、保留和释放 | 跨区/读档/传送/返回稳定，内存趋稳，视觉连续 |
| E：固定长期门禁 | 文档入口、机器预算、CI检查、同机基准与发布前短验收 | 新功能能说明成本，退步能被发现，旧实现可回滚 |

A先行，E的规则从第一项改动开始落实。B/C按实测优先级滚动推进，不为完成阶段名称做无收益改造。D风险最高，只有B/C后仍有显著全城常驻成本才逐区实施。每次提交保持一个可验证假设，不将大型地标扩建混进性能改动。

## 4. 持续运行攻坚

### 优先项：把静态渲染和动态交互的成本区分开

`game/scene-instancing.js`目前保留原对象作为交互来源，同时逐帧遍历合批来源、检查变换、裁剪并上传实例矩阵；原场景矩阵树仍有成本。保留逻辑对象是为了正确性，但静止建筑部件不必按人物关节的方式反复处理。

第一步只选一个重复部件多、交互少的静态区域：由构建者明确登记静态属性，缓存最终变换；实际编辑、父对象移动、显隐或材质变化时显式失效。活动门、楼梯/载具、人物、时段窗光保持动态路径。避免在每帧增加一套昂贵的“是否改变”比较，又把节省抵消。

重复物件优先共享geometry/material/纹理；仅对视觉与渲染状态完全兼容的对象合批。共享材质要区分日夜参数、透明度、颜色空间和个体可变状态，不能让一个对象改颜色影响整片街区。透明玻璃和水面不粗暴混入不透明批次。

按区域、材质及实际可见性测试合批粒度；大批可能增加不可见几何，小批可能增加调用。以整帧耗时和图像为准，不能把“draw calls越少越好”设为唯一目标。[WebGL实践参考](https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API/WebGL_best_practices#batch_draw_calls)

### 随后处理：无变化却每帧重做的工作

- HUD、地图、任务提示、时钟文字与材质参数按变化更新；动画与镜头输入仍及时处理。
- 复用高频临时数组/查询结果，检查垃圾回收尖峰；只优化实测高频路径，避免到处引入对象池。
- 隐藏或远离玩家的装饰动画按需求更新；世界交通、红绿灯、登船、任务和存档时钟继续正确推进。
- 如必须降低远处逻辑频率，先分类“可插值展示”与“会影响碰撞/交互的模拟”，补上重新靠近时的连续恢复；不能简单让远处行人与车辆停止计时。
- 全局更新调度优先复用现有时钟和入口，避免每个新功能各开一组定时器或独立动画循环。

重点回归：骑手不被人群永久堵住、红灯排队恢复、相对行人不抖动僵持、地铁换乘/上下车、船上移动、任务目标人物与建筑编辑。纯算法可要求旧版逐步结果一致；有意改变调度时须说明行为等价边界并验证时钟/相遇/碰撞。

## 5. 加载提速攻坚

### 先减少初始化总工作

当前启动先创建外滩、南京路/地铁、豫园及多个系统，再做烘焙/实例整理/登录背景准备。按真实成本选择：

- 将确定性静态几何、固定文字图集和可复用材质资源提前生成，或直接构造最终批次，减少“创建大量临时mesh再合并”的峰值。对字体、UV、阴影/补光和纹理采样做画面核对；不是把所有现有Canvas文字直接换成低清图片。
- 同样资源只创建一次；共享资源有明确所有者、引用关系与释放规则，场景退出不误销毁仍被使用的纹理。
- 评估预生成网格/图集的下载与内存代价。只对测得值得的首入区域使用，不把整个世界展开成巨大的下载包。
- 暂存或预生成内容必须绑定生成器/格式/内容哈希，沿用92的默认地图与个人编辑分离和失败回退。修改过的区块仍以玩家记录为准。

### 再把启动路径改成“当前旅程所需优先”

保留登录镜头的可见天际线与附近街景，先准备出生/读档位置、必要碰撞、交互与首段剧情。其余区域根据当前位置、路线和下一目标提前准备。

需要先梳理构造依赖：主线、NPC索引、碰撞、地图、存档不能偷偷依赖“所有区域已创建”。将轻量状态/接口与重型画面资源分离；区域未就绪时走统一准备流程。存档在豫园就先准备豫园，在地铁/游轮上则先准备合法落点及载具依赖。开场航拍/过场需要的沿途镜位必须预取，不能突然缺建筑。

分帧能改善响应，但不保证减少总时间；按需准备能减少首入工作，却可能产生下一站卡顿。两者都需同时验证T可玩、前10秒、跨区和全场景就绪时间。

### 下载、着色器与后台任务

- 分析正式GitHub与Sites的真实请求瀑布、压缩和缓存。冷启动、命中缓存、版本切换分别测试。已有内容哈希长期缓存和HTML版本核验应保留。
- 只有证实入口下载/解析显著、且区域依赖已拆开，才做代码分包；避免把一个包拆成大量相互等待的小请求。当前单入口约2.19MB是未计传输压缩的文件大小，不能等同实际下载量。
- 优先预热首入镜头马上需要的着色器、纹理；后续准备在有余量时进行。输入/转头/换区优先，后台任务可取消、可暂停、数量受限。
- 现有地形队列已有手机2ms处理预算和每帧至多一次成品网格提交，继续审计其实际超时/上传成本；不能误认为传入预算就严格满足。大资源需要可切分步骤。
- Worker仅用于测得值得且可传输的纯计算。转移缓冲区优先于复制，设置任务版本与过期结果丢弃；DOM/字体/GPU工作不能假定都能自动搬走。

## 6. 为长期扩建准备的区域规则

不做一次性引擎重写。利用现有区域模块逐步建立统一约定：资源预取、初始化、启用、休眠、释放；持久状态与画面资源分离。命名和具体接口在试点后再定，避免先搭大框架。

每个区域声明边界、依赖、碰撞/任务入口、共享资源、准备成本和释放责任。设置预取缓冲带及短期保留区，避免玩家在边界左右移动反复销毁重建。控制资源缓存总量，并给跨区峰值留预算；不只看稳定站着时的占用。

远景轮廓和当前视距继续保留。预取失败时应保留可玩的已就绪区域并能重试；传送/进站等强制跨区入口必须等待必要地面与碰撞准备，避免落空。恢复同一NPC身份、任务、时刻与载具状态，不能用卸载重生掩盖持续运行问题。

首个试点选择依赖较少的室内或静态街区，成功后再推广到豫园/地铁等复杂区域。新地标应接入此约定，不再默认把所有细节常驻并每帧更新。

## 7. 防止后续开发吃掉优化成果

README是入口，详细规则与机器检查才是持续约束。不能保证永远没有回退，但可以让退步可见、可阻止、可回滚。

| 位置 | 应承担的职责 | 本轮状态 |
| --- | --- | --- |
| `README.md` | 开发入口：画质/存档底线、性能规划链接、开发需附验证证据 | 已添加入口 |
| 本文 | 唯一当前路线、优先级、已知事实与候选边界 | 已建立 |
| 后续 `AGENTS.md`/贡献指南 | 要求开发者读当前性能约定，保留既有接口/预算，并提交相关证据 | 待实施，不扩大本轮修改 |
| 后续性能预算配置 | 机器可读的场景/设备/画质指纹、资源上限与有效基线 | 待测量后建立，不能把猜测写成硬限值 |
| 基准场景与CI | 确定性正确性、资源计数、打包/缓存兼容、性能回归发现 | 现有44项为基础，性能门禁待补 |
| 每次修改的说明 | 改了什么成本、前后结果、画质核对、失败回退及未测环境 | 后续提交要求 |

**必须保留的约束：**

1. 同画质优化保留实际画布、MSAA、材质/贴图清晰度、视距、人数和交通/任务行为；画质调整是独立产品选择，不混入性能收益。
2. 默认城市缓存、玩家方块编辑、背包与主线进度分离；新版本验证旧存档，不能为“更快”跳过编辑记录或覆盖进度。
3. 静态资源内容哈希与HTML版本核验一致；个人存档接口不进入公共长期缓存。发布保留旧哈希资源的合理兼容窗口，避免打开中的旧页面失效。
4. 新功能声明资源归属、活动条件、更新频率和释放入口。重型全城扫描、逐帧建纹理/建几何、大量实时灯或全局常驻内容需要成本证据。
5. 性能基线须随代码、设备、画质和场景签名保存，记录Node/浏览器/渲染库版本及锁定依赖。不能修改基线数值让退步“变绿”，也不能跨设备比较绝对耗时；升级渲染库时必须复核已有驱动诊断修复和着色器准备策略。
6. 保留获益实现的正确性对照与解释。后续大改若替换了算法，应证明新的成本和行为，而不是机械禁止改动旧代码。
7. 测试数据隔离、默认静音、不写真实玩家存档；性能记录不上传私人信息。

**门禁分三层：**

- 每次相关修改：确定性行为测试、资源生命周期/重复创建检查、构建资源和缓存匹配检查。资源计数超预算必须说明原因；允许经审核的内容增长，不能把世界永远冻结在当前数量。
- 性能相关合并：固定环境交替短基准。建议先以同机中位或P95超过基线10%作为复核触发点，重复确认后阻止合并；该阈值需按实际噪声调整。共享CI机器耗时只预警，不能冒充手机FPS硬门禁。
- 发布里程碑：完整相关发布回归、少量固定镜位画质核对、一次真机短路线；调度/资源生命周期大改再做长循环。普通文案和低风险UI调整不要求全城长测。

GitHub和Sites由同一源码提交构建，保持各自原有存档方式；构建完成、源CI成功与线上实际部署成功分别确认。分支开发配独立worktree及预览入口，主分支保留已验证版本；多人协作先同步最新main，避免在共享目录互相覆盖。

## 8. 下一轮具体任务与暂缓项

下一轮从A开始，补当前92发布构建的分段启动和四区固定路线基线，确认目前最大的整帧开销。第一份优化候选建议聚焦静态对象/实例更新或重复场景构造中实测占比更高的一项；只试一个区域，保留前后对照和可回退实现。只有完整收益超过测试噪声、视觉与玩法都通过，才推广及发布。

优先处理已确认的主要开销；若新基线表明上传/透明物GPU成本更大，则调整B的顺序，不坚持预设结论。累计局部百分比不能相加成整机收益。

暂不安排全面换引擎、改WebGPU/WASM、全城Worker化、全场景大合并、默认降分辨率或新增大批内容。它们可能是未来选项，但当前证据不足以承担迁移风险。先完成“首入更快、转头更稳、跨区不堵”的可验证闭环，再扩建新地标。
