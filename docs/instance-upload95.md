# 实例矩阵上传 · 2026-10-23

基线main `8294418`。本轮集中检查外滩完整帧，不改变清晰度、抗锯齿、人数、视距、灯光、地图或存档。

## 根因与修改

`scene-instancing.js` 每帧将可见来源的矩阵紧凑写入实例缓冲前部，并设置 `mesh.count`。原实现只设置 `needsUpdate`，驱动会重复上传整个容量，包括本帧不绘制的尾部。现在每次清理旧上传范围，登记 `[0, count × 16)` 个浮点数。首次GPU分配仍保留完整容量，转头后数量增长时仍能复用；零可见、跳过绘制、来源材质改变及原对象回退路径保持。

测试直接调用仓库所带Three.js的 `WebGLAttributes`，用记录GL缓冲核对首次完整分配、逐帧上传字节及实际GPU矩阵前缀；覆盖数量增长、归零、重新出现、连续未绘制、材质回退和释放。固定容量100、可见4时，后续上传由6,400变为256字节。原实例测试和24个完整城市镜位矩阵/三角形对照继续通过。

## 完整WebGL诊断及限制

本机同画布1055×487、MSAA开启、seed95、静音禁存档的打包测试页，固定路线转动镜头，100帧排除前20帧。记录真实 `bufferSubData` 参数；最终帧读取像素校验仅用于测试，不进入生产循环。

同绘制数量的一组：80帧累计上传18,570,764→11,866,188字节，约减少36.1%；上传调用均为15,635，最终均为2,445次绘制、1,648,780个三角形，像素FNV校验均为2099186550。插桩帧内工作耗时中位32.5→31.5ms，P95为69.7→86.7ms；这是同步帧函数墙钟计时，不是完整显示帧间隔或独立GPU时间。重复运行仍有明显波动，另一基线的区块队列进度和最终绘制数也不同，不能用其耗时夸大收益。

因此本轮确认的是减少无用上传，**没有确认完整帧或手机FPS显著提高，也没有获得新的加载提速结果**。47项现有发布检查及新增上传测试通过，发布脚本纳入后共48项；功能回归不等于真机性能验收。无新增控制台警告/错误，未要求用户操作手机。

## 后续优先级

本机分段中矩阵树约5ms、实例整理约2–3ms、renderer提交/驱动等待约27–40ms，后者不是独立GPU时间。最终帧分类显示，外滩镜位仍提交大量豫园几何（含透明装饰）及街景/人物部件。下一轮先核对这些物件的实际可见性和更新条件，判断能否保持相同画面地减少提交；不能直接缩短视距、移除远处内容或粗暴合并透明材质。

另有重复小几何审计，尚未采用资源共享：先明确逐顶点颜色、可变几何和释放所有权，再按整帧成本决定。未引入未经验证的通用静态变换缓存。原始记录仅本地 `.local-data/qa/upload95-comparison.json`；长期约定见 [性能规划](performance-roadmap.md)。
