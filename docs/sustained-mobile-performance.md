# 手机持续运行优化 · 2026-10-22

基线为 main `5cca7c3`。用户授权通过 USB 采集自己的华为 Pura 70（HarmonyOS 4.2.0、Edge Android 155）游戏性能。本轮不调整画布倍率、抗锯齿、材质、视距或人物数量；存档6、地图11、缓存84保持。

## 定位依据

公开版本的15.84秒真机 CPU 采样记录到约10–11 FPS，帧内中位约88–91ms。道路清理、车辆接触测试和船体碰撞遍历反复检查大量远处对象；场景矩阵更新及驱动程序查询也占有明显时间。此为该手机、浏览器及当时负载的样本，不代表微信或所有设备。

## 实现范围

- `roadContains` 保留原采样点和严格距离边界，先跳过不可能接触的远处点，找到符合点后立即返回，不再计算全部道路的最短距离。
- 船面支撑及船体实体检查先用保守范围排除远处点，同一船体连续表面复用局部坐标，三角函数每次仅计算一组。原洞口、楼梯坡度、活动登船面及高度判断保持。
- 每个交通模拟步建立16格空间索引，仅向原完整车身接触函数提交附近对象；车辆移动后立即更新所在格，仍保护行人、玩家、不同楼层和完整旋转车身。跟车、红绿灯、路线、避让顺序和障碍恢复规则保持。

渲染实例按颜色重组及静态空间拆分候选分别增加了 CPU 工作或绘制调用，均已撤销。场景变换缓存候选虽然矩阵结果相同，但基准更慢，也已撤销。正式渲染路径与基线相同。

## 回归与测量边界

新增 `sustained-runtime.test.mjs`：10,288个道路查询含精确边界、12,000个船面/实体查询、12,000个移动交通接触查询，逐项与发布版谓词对照。既有交通长循环、路口排队、行人/外卖员混行、游轮登船及障碍恢复回归继续通过。

真机专用页静音、隔离存档、固定随机种子及1/30秒模拟步，比较外滩、南京路夜景、陆家嘴、豫园各12帧，舍去每区前三帧。后台地形队列暂时停用以隔离模拟及绘制提交成本，因此结果不能当作正常游玩 FPS、冷启动或完整跨区加载验收。首次 CPU 采样、基准及原始结果仅保留在本地 QA 目录，不上传用户手机信息或游戏数据。

上述完整场景自动对照出现白屏，未取得可靠最终报告，已作废。测试页在离开时主动销毁 WebGL，返回缓存页却没有重建，是其一处明确缺陷；不能据此声称正式版本发生回归，也不能宣称候选通过真机画面验收。后续仅使用不创建 WebGL 的轻量计算对照检查三个热点，仍不能换算游戏 FPS。

轻量页在同一部手机、前台状态下交替原版/候选顺序运行三轮，判断结果全部一致。各自中位耗时如下：

| 工作负载 | 原版 | 候选 |
| --- | ---: | ---: |
| 4,000个道路范围查询 | 472.4ms | 78.1ms |
| 4,000个远距船体实体查询 | 103.2ms | 19.1ms |
| 70辆车、260个对象、30步接触查询 | 67.4ms | 28.9ms |

交通候选计入每步创建索引的成本；船体工作负载主要验证远距排除，接近船体的正确性由原谓词及既有游轮回归覆盖。三轮样本仍受 JIT、温度和后台负载影响，仅支持采用这三个计算优化，不表示游戏整体提升同等比例。未验证总启动等待缩短，正常跨区加载和微信表现仍需实际游玩反馈。

电脑 Chrome 4倍/6倍 CPU 限速和微信 WebView 尚未测试；实际手机 Edge USB 采样已经完成。仍不能承诺所有手机稳定30或60帧。
